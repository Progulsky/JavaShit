# Bridge method

**Related notes:** [[Generic]], [[Method]], [[Type_Erasure]], [[Type_Parameter]]

---

### 1. The Conflict: Polymorphism vs. Type Erasure

Consider this scenario:

```
// After Erasure: setData(Object data)
public class Node<T> {
    public void setData(T data) {
        System.out.println("Node.setData");
    }
}

// Subclass:
public class MyNode extends Node<Integer> {
    @Override
    public void setData(Integer data) {
        System.out.println("MyNode.setData");
    }
}
```

**What happens after compilation (Type Erasure)?**

- In the `Node` class, the method becomes: `void setData(Object data)`.
    
- In the `MyNode` class, your method stays: `void setData(Integer data)`.

**The Crisis:** From the JVM's perspective, `MyNode` no longer **overrides** the parent's method because the argument types (`Object` vs. `Integer`) are different. This is technically **overloading**, not overriding. If you treated `MyNode` as a `Node`, the polymorphism would break, and the parent's method would be called instead of your specific implementation.

---

### 2. The Solution: The Bridge Method

To fix this, the Java compiler automatically generates a "bridge" in the `MyNode` class — an invisible method with the parent's signature that redirects the call to your code.

Here is what the **Bridge Method** looks like "under the hood" (simplified):

```
public class MyNode extends Node<Integer> {
    // Your original method
    public void setData(Integer data) { 
        System.out.println("MyNode.setData"); 
    }

    // THE BRIDGE METHOD generated by the compiler
    public void setData(Object data) {
        // It performs a cast and calls your specific method
        this.setData((Integer) data);
    }
}
```

Now, when you call `n.setData(5)`, the JVM finds the `setData(Object)` method in `MyNode`, which then "bridges" the call to your `setData(Integer)` method. Polymorphism is saved!

---

### 3. How to See It

Since you are familiar with tools like Obsidian for notes and command-line utilities, you can verify this yourself. If you run `javap -c MyNode.class` on your compiled code, you will see methods marked with:

- `ACC_BRIDGE`: Identifies the method as a bridge.
    
- `ACC_SYNTHETIC`: Indicates the method was generated by the compiler, not the programmer.

---

### 4. Interesting Implications

- **Covariant Returns:** Bridge methods are also used if a subclass changes the return type to something more specific (e.g., a method returning `Object` is overridden by one returning `String`).
    
- **Stack Traces:** Sometimes in exception logs, you might see the same method name appearing twice in a row—that is often the execution passing through the bridge.
